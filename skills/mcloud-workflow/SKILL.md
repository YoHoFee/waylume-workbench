# mCloud Work Item Workflow

Use for company requirements, BUGs, and user-assigned work in the local mCloud dashboard. Prioritize the exact existing record and its persisted evidence so resumed work continues from the last verified state. This skill does not grant platform, Git, device, or external-write authorization.

## Responsibility boundary

Modify only confirmed user-owned modules and the smallest direct integration required by the current task. Do not repair, optimize, extend, or rewrite unrelated behavior in another owner's page/module, even when discovered during review. Preserve that owner's existing logic. Before touching another module, record why the task cannot work without that exact integration and keep the change minimal; report adjacent defects and risks to the user and responsible owner instead of fixing them. If a change exceeds the required integration, remove our out-of-scope edits and report any remaining handoff dependency. Before commit, review the diff by file/hunk for ownership and scope. A past failure to avoid repeating: adding continuous automatic pagination to AI music while implementing ID-based selection; pagination behavior belonged to its owner and introduced a concurrent-load risk.

For BUGs, first determine responsibility from the persisted workbench scope catalog. Reuse still-applicable confirmed boundaries; add evidence or a candidate match to each new BUG without expanding responsibility from assignee or code history. Unknown, suspected out-of-scope, or conflicting scope evidence stops scope-dependent repair and reproduction. If in scope, read the source and original issue materials, then apply the dual-confidence and batch route in [references/bug-confidence.md](references/bug-confidence.md). This route does not relax post-fix acceptance or task-specific restrictions. Keep the entry brief and consult the reference only for BUG work.

## Troubleshooting knowledge

At the start of work, check only the entries in [references/troubleshooting.md](references/troubleshooting.md) that match the current environment, device/UI, platform write, scheduling/handoff, or code/business path. For a known symptom, use its linked canonical evidence and shortest supported handling before investigating again. Do not reread the full lessons file by default. After a fix, add or correct an experience only when its cause and handling have sufficient evidence; mark unresolved or contradicted explanations tentative and retain the evidence gap. Historical lessons never override the user's latest authorization, assigned responsibility, current C/F decision, batch boundary, or visual acceptance requirements.

## Parallel Git workspace (mandatory)

Before claiming, starting, or resuming any code task, read [parallel Git worktree protocol](references/parallel-git-worktree.md). Main checkout is integration-only; every requirement/BUG uses its own `local/` branch and its own worktree under `~/.codex/worktrees/`. The task context must contain record ID, branch, base, worktree, owner and build owner; if any is missing, stop and ask the Lead to allocate before editing. Do not edit the main checkout, share one branch across worktrees, clean another worktree, or start a concurrent build/device operation. The existing `~/.dsh/WORK_ASSISTANT.md` section 7 branch baseline/naming/push/merge rules remain in force; this protocol only adds workspace isolation.

## Execute and close

- On the first BUG dispatch, include the canonical skill path `/Users/mr.yao/.codex/work-agent/tools/mcloud/dashboard/skills/mcloud-workflow/SKILL.md`, the exact BUG ID, the already-granted authorization and its limits, and the existing batch ID (or state that no batch applies). Give the executor the routing task, not a proposed diagnosis or repair answer. The executor reports the skill revision read (use a file hash when no explicit revision is declared), matched scope ID/catalog revision and selected C/F route in the original BUG record. The main agent checks the actual actions and saved evidence against that route; “I read the skill” alone is not proof of compliance.
- For an existing company `work` or `bug`, claim and update its existing dashboard record. Read its current record `revision`, then use the README-documented `agent-claim` / `agent-update` compare-and-set operation with the real executing agent's `CODEX_THREAD_ID` identity; do not substitute `CODEX_SESSION_ID` or invent an identity. Use the returned record revision for each next write. During actual execution, report a meaningful phase or use a documented heartbeat; do not heartbeat while merely waiting or reading. On completion or a blocked handoff, report the actual outcome and release the claim with the current revision. On a revision conflict, reread the item before deciding whether a write is still needed.
- Keep one code writer for shared source. Assign a unique owner to each shared resource (Git/build, issue browser, device/PUA). For batch device work, serialize one device owner across the frozen batch, use one integrated build/install, then record separate acceptance evidence per BUG; see the confidence reference. Read-only analysis may run in parallel. Do not split the same investigation across agents or ask another agent to repeat it. Use one independent, targeted review of the relevant diff; after a fix, revisit only affected findings.
- A build/package may serve multiple BUGs sharing the same change, but retain a separate reproduction, expected observation, actual result, evidence, and limitation for every BUG. Use a screenshot when one stable visual state proves the requirement; use a continuous recording for flows, scrolling, ordering, transitions, or transient behavior. Do not claim a screenshot proves a dynamic sequence, and do not infer that an attachment was reviewed from its manifest.
- Do not infer QA pass, acceptance, or closure from prose in `latest_brief`, `context.md`, a static review, or submission-to-test status. Report those states only from explicit, attributable QA/platform evidence. Preserve unknown or untested boundaries.
- After one valid reproduction attempt fails to reproduce, apply the C/F boundary in the confidence reference: C > 80 may support only a tentative minimal repair when F and A conditions are met; C <= 80 waits for direction. A reproduction never proves root cause. When a device, API, build, or UI state has not changed, do not blindly repeat the same failed action. Stop on target-ID mismatch or unsafe write state; do not guess a compensating write.
- Perform the work authorized for this turn; do not ask again for authorization already given. Git commit/push, platform writes, and device actions remain subject to the user's specific authorization and the project workflow. Do not default to a full project build or tests.
- Report the outcome in the existing record using only documented dashboard commands and their actual supported fields. Keep code, QA, Git, platform, and completion states distinct. End with a compact handoff: `ID | owner | conclusion | changed files | verification/evidence | untested/blocker | authorization | next action`.
- In this Codex environment, `send_message` to an already completed agent only queues a message; it does not resume execution. Use `followup_task` to reactivate that agent and confirm it is running before treating it as an active handoff. Other hosts may have a different resume mechanism.
